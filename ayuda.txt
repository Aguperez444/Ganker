User Story — Chat de equipo (chatroom)

Story
Como miembro de un equipo, quiero enviar y recibir mensajes en tiempo real dentro del chat exclusivo de mi equipo, para coordinar estrategias, horarios y comunicarme con mis compañeros.

Contexto
- Cada equipo tiene una única sala de chat grupal (chatroom), creada junto con el equipo.
- Solo los miembros del equipo forman parte de esa sala.
- La recepción en tiempo real funciona por WebSocket; el historial se guarda y se consulta por HTTP contra la base de datos.
- Las conversaciones privadas (1 a 1) son un flujo aparte y no se mezclan con las salas de equipo.

Criterios de aceptación
1. Solo un usuario autenticado que sea miembro del equipo asociado a la sala puede leer y enviar mensajes. Si no es miembro, la operación se rechaza con un error de permisos.
2. El mensaje no puede estar vacío (se considera vacío también si contiene solo espacios).
3. El mensaje no puede superar el límite máximo de 2000 caracteres.
4. Los mensajes válidos se almacenan en la base de datos y quedan disponibles en el historial de la sala.
5. Los mensajes se entregan en tiempo real a los demás miembros conectados a la sala.

Pendiente
- Si el equipo fue disuelto o desactivado, no se debe permitir enviar nuevos mensajes.
  (No implementado: por ahora no existe la acción de disolver un equipo y el acceso al chatroom no valida que el equipo siga activo.)
- Interfaz de chat de equipo en el frontend.
  (No implementado: el chat de la aplicación hoy solo cubre conversaciones privadas 1 a 1. Los endpoints de WebSocket e historial del chatroom existen en el backend y unirse a un equipo devuelve su chatroom_id, pero la UI todavía no tiene un punto de entrada a la sala del equipo.)
- Mensaje de error específico al superar los 2000 caracteres.
  (El rechazo funciona, pero el backend responde con el mensaje de "no puede estar vacío" porque agrupa los errores de validación del mensaje.)

Pruebas de usuario
1. Enviar un mensaje de texto válido siendo miembro del equipo.
   Resultado esperado: el mensaje se envía, se guarda y se muestra en la sala.
2. Enviar un mensaje a una sala de un equipo al que el usuario no pertenece.
   Resultado esperado: la operación se rechaza con un error de permisos.
3. Enviar un mensaje vacío o con solo espacios.
   Resultado esperado: se rechaza con el error "El mensaje enviado no puede estar vacío".
4. Enviar un mensaje que supere los 2000 caracteres.
   Resultado esperado: se rechaza y no se envía.
5. Intentar enviar un mensaje a una sala de un equipo disuelto o desactivado.
   Resultado esperado: pendiente de implementación.
Nota: las pruebas 1 a 4 se pueden verificar a nivel API/backend; todavía no existe una UI de chat de equipo que las ejerza desde la aplicación (ver Pendiente).



User Story 2 — Historial de mensajes del chatroom

Story
Como miembro de un equipo, quiero consultar el historial de mensajes de la sala de chat de mi equipo, para poder revisar conversaciones pasadas, coordinaciones o acuerdos previos.

Contexto
- El historial se consulta por HTTP contra la base de datos y no depende de estar conectado al WebSocket.
- Los mensajes se devuelven del más nuevo al más viejo y paginados (tamaño máximo de página: 100).
- La UI permite cargar páginas anteriores ("Cargar mensajes anteriores") sin salir de la sala.

Criterios de aceptación
1. Solo un usuario autenticado que sea miembro de la sala puede consultar su historial; si no es miembro, la operación se rechaza con un error de permisos.
2. La respuesta del historial debe traer, por cada mensaje: id del mensaje, id de la sala, emisor (id, username, nombre y avatar) y contenido y timestamp.
3. Los mensajes se ordenan del más nuevo al más viejo y se devuelven paginados; la UI debe permitir cargar mensajes anteriores sin duplicar los ya mostrados.
4. Consultar el historial de una sala inexistente o el de una conversación privada tratada como chatroom devuelve un error de no encontrado.
5. Los mensajes del historial quedan disponibles de forma persistente aunque el emisor ya no esté en línea.

Pendiente
- Interfaz de sala de equipo en el frontend para consumir este historial.
  (No implementado: el backend expone el historial del chatroom cumpliendo todos los criterios, pero la UI que permite "cargar mensajes anteriores" hoy funciona solo sobre conversaciones privadas 1 a 1. Falta conectar la sala del equipo a este endpoint.)

Pruebas de usuario
1. Consultar el historial siendo miembro del equipo.
   Resultado esperado: se muestran los mensajes de la sala con su contenido, emisor y hora.
2. Consultar el historial de una sala de la que el usuario no es miembro.
   Resultado esperado: la operación se rechaza con un error de permisos.
3. Consultar el historial de un chatroom inexistente o de una conversación privada.
   Resultado esperado: se devuelve un error de recurso no encontrado.
4. Abrir una sala con muchos mensajes y cargar más anteriores.
   Resultado esperado: se agregan los mensajes anteriores sin duplicados y se mantiene la posición de lectura.



User Story 3 — Buscar equipos

Story
Como jugador, quiero buscar equipos para encontrar uno al que me pueda incorporar.

Contexto
- El listado proviene del endpoint de búsqueda de equipos (GET /api/v1/teams) y solo incluye equipos activos con al menos un cupo vacante.
- Cada equipo devuelve, además de sus datos, si el jugador que consulta puede unirse y el motivo en caso contrario.

Criterios de aceptación
1. Se debe mostrar un listado de los equipos activos que cuenten con cupos vacantes.
2. Cada tarjeta de equipo debe exhibir: nombre, mensaje descriptivo, ícono/avatar, rango representativo, rangos mínimo y máximo, contador de jugadores (por ejemplo, 4/5), cantidad de vacantes, roles disponibles, videojuego y región.
3. Se debe permitir filtrar el listado por videojuego, región y rango.
4. Se debe permitir filtrar por la cantidad de espacios vacantes del equipo.
5. Se debe permitir filtrar por los roles disponibles en los slots vacantes del equipo.
6. Se debe permitir buscar equipos por texto, con coincidencias en el nombre o en la descripción.
7. Cada tarjeta debe mostrar el botón "Unirse al equipo".
8. Si el jugador no cumple los requisitos (rango fuera del mínimo/máximo, restricción de región, ya es miembro o ya pertenece a otro equipo activo), se debe indicar el motivo y no permitir el ingreso directo.
9. Si no existen equipos que coincidan con los filtros o la búsqueda, se debe mostrar un mensaje informando que no se encontraron resultados.
10. Se debe permitir limpiar/restablecer los filtros para volver a ver el listado completo de equipos disponibles.

Pruebas de usuario
1. Ingresar a la sección de búsqueda y visualizar el listado de equipos con sus datos, integrantes, vacantes y contador de jugadores.
   Resultado esperado: el listado se muestra correctamente.
2. Filtrar equipos por rango o región donde existan equipos disponibles.
   Resultado esperado: el listado se filtra y muestra los equipos que cumplen el criterio.
3. Buscar un equipo por nombre o palabra clave existente.
   Resultado esperado: aparecen los equipos cuyo nombre o descripción coincide.
4. Buscar o filtrar con criterios que no coincidan con ningún equipo.
   Resultado esperado: se muestra el mensaje de "sin resultados".
5. Visualizar equipos cuyos requisitos no coinciden con el perfil del jugador.
   Resultado esperado: se indica el motivo y no se permite el ingreso directo.
6. Limpiar los filtros aplicados.
   Resultado esperado: se recarga el listado general de equipos disponibles.



User Story 4 — Modificar equipo

Story
Como creador de un equipo, quiero modificar la información del equipo para mantenerla actualizada.

Criterios de aceptación
1. Solo el creador/líder del equipo puede modificar la información; un integrante regular o un usuario ajeno debe recibir un error de permisos.
2. Se debe permitir modificar el nombre del equipo (obligatorio, hasta 100 caracteres) y el mensaje o descripción de búsqueda (hasta 500 caracteres).
3. Se debe permitir modificar el rango mínimo y el rango máximo requeridos para ingresar al equipo.
4. Se debe permitir modificar la opción de admitir jugadores de otras regiones y cambiar la región del equipo.
5. No se debe permitir cambiar el videojuego asignado al equipo desde esta funcionalidad.
6. Se deben validar los campos obligatorios (nombre y rangos) para que no queden vacíos.
7. Se debe validar que el rango mínimo no sea superior al rango máximo.
8. Se debe validar que el nuevo intervalo de rangos sea compatible con el rango actual del líder y de los integrantes activos del equipo.
9. Si algún dato no cumple las validaciones, no se deben aplicar los cambios y se debe notificar el error correspondiente.
10. Al confirmar, los datos deben guardarse en la base de datos y el listado general de equipos debe actualizarse.
11. El creador debe recibir un mensaje de confirmación cuando el equipo haya sido modificado exitosamente.

Pruebas de usuario
1. Modificar la información del equipo con datos válidos siendo el creador.
   Resultado esperado: los cambios se guardan y se confirma la modificación.
2. Intentar modificar el equipo siendo un integrante regular o un usuario ajeno.
   Resultado esperado: la operación se rechaza con un error de permisos.
3. Modificar el nombre del equipo dejándolo vacío.
   Resultado esperado: se rechaza y no se aplican cambios.
4. Establecer un rango mínimo superior al rango máximo.
   Resultado esperado: se rechaza y no se aplican cambios.
5. Configurar un intervalo de rangos que excluya el rango actual de algún integrante del equipo.
   Resultado esperado: se rechaza y no se aplican cambios.
6. Modificar solo la descripción y el permiso de región sin alterar los rangos.
   Resultado esperado: los cambios se guardan y se confirma la modificación.
